QMD is a search engine for your Markdown knowledge base. Its purpose is to help you find the right information inside a collection of Markdown files using more than simple keyword matching.

Imagine you have an Obsidian vault containing 5,000 Markdown files about your metro organization:
- Equipment manuals
- Maintenance reports
- Meeting notes
- Technical specifications
- Knowledge pages generated by your LLM Wiki
- Relationships between equipment, stations, and incidents
You ask Hermes:
What were the recurring causes of overheating in the ventilation motors at Line 1 stations?

A simple file search might look for the exact words overheating and ventilation motor. But the relevant information might be written as:
- Motor temperature exceeded the operating limit.
- Cooling fan failure caused thermal problems.
- Excessive bearing friction increased operating temperature.
- Ventilation unit experienced abnormal heat.
The problem is that these documents may describe the same concept using different words.

QMD tries to solve this search problem by combining different search techniques.

Let's build the idea from the beginning.
1. First, what problem does QMD solve?
Let's start without AI.

Suppose your Obsidian vault contains these files:
Metro-Knowledge/ (Equipment/: Ventilation-Motor-VM-102.md, Ventilation-Motor-VM-103.md, Cooling-System.md; Maintenance/: Report-2026-001.md, Report-2026-002.md, Report-2026-003.md; Meetings/: Maintenance-Meeting-January.md, Maintenance-Meeting-February.md)

Markdown is just a text format. Each file contains text, headings, lists, tables, links, and possibly metadata.

If you have 20 files, you can search them manually. If you have 20,000, that becomes difficult.

You need a system that can:
1. Read and understand the files' structure.
2. Build an index so it doesn't have to scan every file for every question.
3. Find relevant passages when someone asks a question.
4. Rank the results so the most useful information appears first.
5. Give those results to Hermes or another LLM.
That's the job of QMD.
The central idea
Your Markdown files (Obsidian vault, documentation, reports, notes) -> QMD indexing (Extract text, split into searchable pieces, build indexes) -> QMD search (Keyword search + semantic search + ranking) -> Relevant passages (Returned to Hermes as evidence for answering)

QMD is not a special Markdown format. It works with ordinary Markdown files and creates its own search indexes.

2. Understand the three fundamental search techniques
This is the most important part of learning QMD. It combines three ideas:
- BM25: keyword search.
- Vector search: semantic search.
- Reranking: judging which retrieved results are most relevant.
A. BM25 — finding words
BM25 is a traditional information-retrieval algorithm. It searches for words and ranks documents according to how relevant their terms are to your query.
Documents: A "Ventilation motor VM-102 experienced overheating." B "Cooling fan failure caused high motor temperature." C "Station lighting system requires inspection."
Your question: Find reports about ventilation motor overheating.
BM25 looks for terms such as ventilation, motor, overheating. Document A has a strong match because it contains those exact terms. Document B might receive a weaker score because it contains motor and temperature, but not the exact terms ventilation and overheating. Document C probably receives a very low score.
Strength: Excellent when you know exact words, equipment IDs, model numbers, names, or technical terminology.
Weakness: It doesn't inherently understand that two different expressions can describe the same concept.
B. Vector search — finding meaning
Now imagine you ask: Which maintenance reports describe motors becoming unusually hot?
The relevant document says: The cooling fan failed, causing the motor temperature to exceed its normal operating range.
Notice something interesting: the document doesn't contain the exact phrase "motors becoming unusually hot." A conventional keyword search might miss it.
Vector search uses a model called an embedding model. An embedding model converts text into a numerical representation called a vector.
Sentence 1 "The motor is overheating." -> 0.82 0.15 0.67 0.34 0.91
Sentence 2 "The motor temperature exceeded its normal limit." -> 0.79 0.19 0.71 0.31 0.87
Illustrative numbers only, not actual QMD embeddings.
The important idea is that sentences with similar meanings tend to have vectors that are close to each other in the embedding space.
Mathematically, one common way to measure this closeness is cosine similarity: cosine(A,B) = A·B / (||A|| ||B||)
You don't need to understand all the mathematics yet. The essential point is: BM25 compares words. Vector search compares numerical representations of meaning.
Strength: Finding concepts, paraphrases, and natural-language descriptions.
Weakness: It can miss exact technical identifiers or confuse similar but distinct things. For example, two different motor models may have very similar descriptions.
C. Reranking — deciding which results are best
Suppose QMD retrieves 20 possible passages. A reranker takes the original question and each candidate passage and evaluates how well they match.
VM-102 overheating due to bearing failure: Very relevant; Cooling fan inspection procedure: Relevant; General motor maintenance instructions: Somewhat relevant; Station lighting inspection: Not relevant
BM25 and vector search are responsible for finding candidates. The reranker is responsible for judging those candidates more carefully.

3. How does QMD combine them?
1. Original question -> 2. Query expansion -> 3A. BM25 / 3B. Vector search -> 4. Result fusion (RRF) -> 5. LLM reranking -> 6. Final search results returned to Hermes
RRF (Reciprocal Rank Fusion) is an algorithm for combining multiple ranked result lists. BM25 gives A, B, C; vector gives C, A, D. RRF combines their rankings, rewarding documents that appear near the top of either list, without requiring comparable score scales.

4. Before searching, QMD must prepare your documents (indexing)
Step 1: Register a collection: qmd collection add ~/Metro-Knowledge --name metro (several collections: personal, metro, meetings, projects)
Step 2: Read and split the documents into chunks (System overview, Motor specifications, Cooling mechanism, Common failures, Maintenance procedures). Retrieve relevant pieces, not whole documents.
Step 3: Build the indexes: A. Full-text index (BM25). B. Vector index (embeddings of chunks). Original Markdown files remain the source documents.
Step 4: Update the indexes when documents change.

5. What is query expansion?
Question "Why does the ventilation motor get hot?" vs terminology: thermal overload, excessive operating temperature, bearing friction, cooling failure, motor overheating. QMD can use a query-expansion model to generate additional search expressions. Typed expansions: lexical to keyword search, semantic and hypothetical-document expansions to vector search.
HyDE (Hypothetical Document Embeddings): the LLM generates a hypothetical passage, it is embedded, and vector search looks for real passages with similar meaning. Important: the hypothetical passage is only a search aid. It is not evidence.

6. How does Hermes communicate with QMD?
Through MCP. Hermes understands the question and decides what to do; QMD searches and retrieves. Flow: understand question, recognize need for documents, call QMD search, receive passages, maybe retrieve full documents, analyze evidence, answer with source references. QMD is responsible for retrieval; Hermes for orchestration and answer.

7. What QMD is — and what it isn't
Obsidian: edit and organize Markdown; QMD: search Markdown; Embedding model: text to vectors; Reranker: relevance; Hermes: coordinate and answer; LLM Wiki: synthesized knowledge; Original document storage: authoritative sources.
QMD does not automatically: understand your entire organization; build a complete knowledge graph; decide whether a report is technically correct; create a reliable summary of every document; replace your original documents; guarantee that a retrieved passage is factually correct. It is a retrieval component, not the entire knowledge-management system.

8. Commands: npm install -g @tobilu/qmd; qmd collection add ~/Obsidian/Metro-Knowledge --name metro; qmd embed; qmd search "ventilation motor overheating"; qmd vsearch "Why are ventilation motors becoming too hot?"; qmd query "What are the main causes of ventilation motor failures?"; qmd get "metro/Maintenance/Report-2026-001.md". search=BM25, vsearch=vector, query=hybrid+reranking.

9. QMD in the metro architecture: sources -> document processing -> LLM Wiki -> Obsidian/Markdown vault -> QMD -> MCP -> Hermes. Keep original reports, letters and manuals in a separate authoritative store; QMD searches the wiki, another retrieval system (Document RAG) searches originals when exact evidence is required.

10. Learning order: Information Retrieval, Inverted Index, BM25, Embeddings, Vector Similarity, Chunking, RRF, Reranking, MCP. Free textbook: Introduction to Information Retrieval (Stanford). Don't start by installing QMD; understand BM25, embeddings and vector similarity first. The next concept: the inverted index.
